# Accounts board — proposal 2

Four filters: Todas (current groups), Pagadas (fully paid current groups), Pendientes (positive balance), Historial (groups included in generated reconciliations). Newest activity first; current paid cards are green, positive balances red, each with explicit labels. Total is distinct from outstanding debt. Empty manually created accounts are current and labeled Sin consumos, not counted as paid. Search retains the filter. Archived groups show the report number and Enviado/Devuelto/Confirmado separately from debt status.

New secured fridge_account_board RPC projects groups of existing operations by customer and reconciliation ID; standalone legacy sales group by operation ID. No records are copied or moved. New consumption after a report opens a new current group while preserving that customer's archived group. Group detail uses only that group's recorded operations and historical prices. The existing account payment form continues to use current customer balance.

Only draft reconciliation selection changes: a sale/payment tied to a customer with positive balance remains unassigned, including partial receipts. Once settled, all remaining unassigned sales/payments become eligible together. Already linked operations and immutable report snapshots are never regenerated or reassigned. Generation archives only selected groups, even before manager receipt; returned and confirmed reports retain distinct statuses. Cash for a partially paid account remains a recorded receipt but is held for a later reconciliation. Stock/debt reference sections remain informational; debt is never treated as received money. Existing fund/pricing wrappers still calculate from the filtered operation IDs. Generation remains fingerprint-validated under the existing transaction lock.

The reconciliation landing amount now uses eligible draft receipts, rather than including receipts held for pending accounts or already sent reports. No stock, sale, collection, customer, report or payout mutation is performed by this migration. The user test sale remains intact; its pretest baseline remains separate.

Verification: PGlite covers paid/partial groups, archive on generation, held partial receipts, final settlement, no double inclusion, reopening after an archived cycle, denied unauthorized/anonymous access. UI tests cover filters, scope-preserving search, historical receipt totals and payment UI. Existing mobile cart and reconciliation tests remain. Source/DOM verification only; no physical-device review is claimed. Rollback SQL and frontend revert must be coordinated.
